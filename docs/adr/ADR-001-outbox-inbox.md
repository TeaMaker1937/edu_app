# ADR-001: Transactional Outbox + Idempotent Inbox

## Статус
Принято (2026-10-23). Действует для `enrollment`, `education-platform`.

## Контекст

**Проблема.** Платная запись требует **транзакционной согласованности** между БД и RabbitMQ. Прямой `publish` после `commit` не гарантирует: если процесс упадёт или брокер недоступен в момент публикации, событие `EnrollmentConfirmed` потеряется навсегда, а `enrollment` уже сохранён. Обратный порядок (`publish` → `commit`) даёт противоположный риск: событие ушло, а данные откатились — downstream видит запись, которой нет.

**Дополнительно:** RabbitMQ гарантирует **at-least-once** доставку. Consumer может получить одно и то же сообщение дважды (redelivery после потери ACK, ручной повтор, переподключение брокера). Без дедупликации это создаёт дубликат эффекта — например, повторное уведомление пользователю.

**Требования:**
1. Изменение данных и событие о нём — атомарно (либо оба есть, либо оба нет).
2. Публикация не должна блокировать основной flow — падение RabbitMQ не должно откатывать запись на курс.
3. Одно событие `eventId` — **ровно один эффект** у каждого обработчика, независимо от числа доставок.

## Рассмотренные альтернативы

### A. Direct publish после commit

- **Плюсы:** простой код, нет outbox-таблицы.
- **Минусы:** потеря события при крахе между COMMIT и publish; нужно ручное восстановление.
- **Когда подходит:** одиночный сервис без durability-требований, потери событий допустимы.

### B. Two-Phase Commit (XA)

- **Плюсы:** строгая атомарность на уровне БД+брокер.
- **Минусы:** медленно, требует XA-драйвера, сложно с RabbitMQ; при падении координатора — блокировка до timeout.
- **Когда подходит:** банковские системы, где нельзя компенсировать вручную. Для остального — антипаттерн (Pat Helland: *"Life Beyond Distributed Transactions"*).

### C. Transactional Outbox + Idempotent Inbox **(выбрано)**

- **Плюсы:**
    - Атомарность без 2PC (одна локальная БД-транзакция).
    - Публикация не блокирует основной flow (relay асинхронный).
    - At-least-once публикация + идемпотентный consumer = **effectively exactly-once по эффекту**.
    - Relay поддерживает lease → нет дублей даже с 2 экземплярами.
- **Минусы:**
    - Дополнительная таблица + процесс relay + inbox-таблица у каждого consumer.
    - Латентность публикации (тик 2s) — приемлемо для нашей нагрузки.
    - Требуется периодическая очистка `outbox_events` / `inbox_events` (retention).

## Критерии сравнения

| Критерий | A. Direct | B. 2PC | **C. Outbox+Inbox** |
|---|---|---|---|
| Гарантия «данные+событие» | ❌ | ✅ | ✅ |
| Latency impact | низкая | **высокая** | средняя (~2s на relay) |
| Complexity | низкая | **высокая** | средняя |
| Потеря события при крахе | ✅ (плохо) | нет | нет |
| Дубликаты у consumer | есть | нет | **отсекаются inbox** |
| Работает без XA | — | ❌ требует | ✅ |
| Recovery после restart | ручной | сложный | ✅ автоматический |

## Последствия

**Положительные:**
- `EnrollmentConfirmed` не теряется при недоступности RabbitMQ — хранится в `outbox_events` и будет опубликован relay'ем после восстановления.
- Повторная доставка не создаёт дубликат (эксперимент 1.1 vs 1.2 — см. отчёт).
- Relay масштабируется: два экземпляра не публикуют одно событие дважды (lease через conditional `UPDATE ... WHERE locked_until < now`).

**Отрицательные / обязанности:**
- Retention: держать `published_at IS NOT NULL` N дней для аудита, потом чистить. `inbox_events` — аналогично. Без этого таблицы растут бесконечно.
- SLA публикации зависит от relay — если relay не запущен, события копятся. Метрика: `outbox_events WHERE published_at IS NULL` + алерт на рост > 100.
- Consumer обязан **применять эффект в одной транзакции с `INSERT inbox`** — иначе pattern не работает.

## Когда пересмотреть

1. **Смена брокера** на тот, что поддерживает transactional producer (Kafka `enable.idempotence=true` + `transactional.id`) — можно упростить до single-producer exactly-once.
2. **Уход от Postgres** — например, на DynamoDB — outbox-паттерн сложнее (нужен streams или DynamoDB Streams).
3. **Multi-region актив-актив** — conditional UPDATE `tryLock` в outbox становится слабым местом, нужны глобальные локи (Spanner, CockroachDB).
4. **Нагрузка** вырастет настолько, что relay на 2s становится узким местом — нужен CDC (Debezium) вместо polling.
5. **Отказ от async вообще** — переход на gRPC sync вызовы упрощает согласованность (но создаёт другие проблемы — resilience).
